# Протокол обмена данными АМС

## Система мониторинга телекоммуникационной вышки

**Версия документа:** 1.1.0

**Назначение:** документ описывает формат и правила обмена данными между IoT-устройством
(AMS) и удалённым MQTT-сервером (EMQX).

---

## 1. Архитектура обмена данными

```
+----------------+      локальный MQTT       +----------------+      удалённый MQTT      +----------+
|   Воркеры      |  ─────────────────────>   |   Агрегатор    |  ─────────────────────>  |  Сервер  |
| (датчики)      |   127.0.0.1:1883          | mqtt_aggregator|    REMOTE_BROKER          |  EMQX    |
|                |   QoS 0                   |                |    QoS 1                  |          |
+----------------+                           +----------------+                           +----------+
```

**Компоненты:**

| # | Компонент                   | Роль                                                              |
|---|-----------------------------|-------------------------------------------------------------------|
| 1 | Воркеры (датчики)           | Публикуют первичные данные датчиков в локальный MQTT-брокер       |
| 2 | Локальный MQTT (Mosquitto)  | Внутренняя шина обмена на устройстве, `127.0.0.1:1883`, без TLS   |
| 3 | Агрегатор (mqtt_aggregator) | Сбор, агрегация, отправка телеметрии, генерация алертов, watchdog |
| 4 | Удалённый MQTT (EMQX)       | Конечная точка приёма данных на сервере                           |

Все сообщения — **JSON**, кодировка **UTF-8**.

---

## 2. Транспортный уровень

| Параметр                | Значение                                                  |
|-------------------------|-----------------------------------------------------------|
| Протокол                | MQTT v3.1.1 / v5                                          |
| Адрес локального брокера| `127.0.0.1:1883`                                          |
| TLS (локальный)         | Отсутствует                                               |
| Адрес удалённого брокера| Задаётся в коде: `REMOTE_BROKER:REMOTE_PORT`              |
| Локальная аутентификация| Логин: `ams_iot`, пароль: `ams_iot_pass`                  |
| Удалённая аутентификация| Задаётся в коде: `REMOTE_USER` / `REMOTE_PASS`            |
| QoS (удалённая отправка)| **1** — гарантированная доставка (at least once)          |
| QoS (локальная отправка)| **0** — максимальная производительность (fire and forget) |
| Keepalive               | 60 секунд                                                 |

## 3. Процедура регистрации устройства

При первом запуске устройство не имеет постоянного идентификатора (`device_id`).
Процедура выполняется автоматически, участие backend-разработчика требуется на шаге 4.

### Шаг 1. Генерация временного UID

Агрегатор создаёт временный идентификатор: `TEMP-{MAC6}-{rand4}`

- `MAC6` — последние 6 символов MAC-адреса (`eth0` или `wlan0`), без двоеточий, нижний регистр
- `rand4` — случайное 4-значное число от 1000 до 9999
- Пример: `TEMP-a1b2c3-4729`

### Шаг 2. Подписка на команды регистрации

Агрегатор подписывается на топик:

```
ams-reg/{temp_uid}/command
```

### Шаг 3. Публикация статуса регистрации

Каждые **60 секунд** агрегатор отправляет в топик `ams-reg/{temp_uid}/telemetry` (QoS 1):

```json
{
  "uid": "TEMP-a1b2c3-4729",
  "status": "registering"
}
```

**Обработка на сервере:** при получении сообщения с `"status": "registering"` сервер должен
либо автоматически назначить UID, либо поместить устройство в очередь на ручную активацию
через админ-панель.

### Шаг 4. Назначение постоянного UID (сервер → устройство)

Сервер отправляет команду в топик `ams-reg/{temp_uid}/command` (QoS 1):

```json
{
  "command": "set_uid",
  "uid": "AMS-000001"
}
```

**Рекомендуемый формат постоянного UID:** `AMS-XXXXXX`, где `XXXXXX` — 6-значный порядковый
номер (например, `AMS-000001`, `AMS-000042`).

### Шаг 5. Сохранение и перезагрузка

Агрегатор сохраняет полученный `uid` в файл `~/fw_settings/uid.json`:

```json
{"uid": "AMS-000001"}
```

…и выполняет `sudo reboot`.

### Шаг 6. Переход в основной режим

После перезагрузки агрегатор читает `uid.json` и переходит в штатный режим работы
с `device_id = "AMS-000001"`.

### Таймаут регистрации

Если за **300 секунд** (5 минут) постоянный UID не получен, агрегатор перезапускается
и генерирует новый временный UID. Сервер должен быть готов к повторной регистрации
того же физического устройства под новым временным идентификатором.

### Итоговые топики зарегистрированного устройства

| Назначение          | Топик                          | Направление         |QoS|
|---------------------|--------------------------------|---------------------|---|
| Телеметрия          | `ams/{device_id}/telemetry`    | Устройство → Сервер | 1 |
| Алерты              | `ams/{device_id}/alert`        | Устройство → Сервер | 1 |
| Команды             | `ams/{device_id}/command`      | Сервер → Устройство | 1 |

Где `{device_id}` — постоянный идентификатор, например `AMS-000001`.

## 4. Формат телеметрии

### 4.1. Общие сведения

| Параметр         | Значение                              |
|------------------|---------------------------------------|
| Топик            | `ams/{device_id}/telemetry`           |
| QoS              | 1                                     |
| Периодичность    | 60 секунд (настраивается: `INTERVAL`) |
| Формат           | JSON                                  |
| Кодировка        | UTF-8                                 |
| Макс. размер     | ~2 КБ (оценочно)                      |

### 4.2. Правила формирования

- Поля, **все** значения которых `null`, исключаются из JSON целиком.
- Пустые объекты `{}` исключаются из JSON целиком.
- Порядок полей не гарантирован, сервер должен парсить JSON как неупорядоченный словарь.

### 4.3. Полный пример сообщения

```json
{
  "device_id": "AMS-000001",
  "fw_version": "1.1.0",
  "temperatures": {
    "00-740000000000": "HDW:45.2, OUT:23.5",
    "00-b40000000000": "HDW:44.8, OUT:22.9"
  },
  "distance_mm": 1250,
  "power_phases": {
    "L1": true,
    "L2": true,
    "L3": false
  },
  "battery": {
    "battery_state": "charging"
  },
  "wind": {
    "wind_speed_mps": 12.3
  },
  "tilt": {
    "tilt_degrees": 0.8
  },
  "system_power": {
    "bus_voltage_v": 5.023,
    "current_ma": 120.5,
    "power_mode": "charging"
  }
}
```

### 4.4. Описание полей

#### `device_id` (string, обязательно)

Уникальный постоянный идентификатор вышки, назначенный при регистрации.
Формат: `AMS-XXXXXX`.

#### `fw_version` (string, обязательно)

Версия прошивки устройства. Берётся из файла `fw_settings/VERSION`.
Формат: `X.Y.Z` (SemVer).

#### `temperatures` (object, опционально — отсутствует, если нет датчиков)

Словарь показаний 1-Wire датчиков DS18B20.

- **Ключ:** серийный номер датчика DS18B20 в формате `XX-XXXXXXXXXXXXXXXX` (hex), например `00-740000000000`.
- **Значение:** строка `"HDW:{t1}, OUT:{t2}"`, где:
  - `t1` (float) — температура внутри корпуса оборудования, °C
  - `t2` (float) — температура окружающей среды, °C

Если физически установлен один датчик, оба значения могут совпадать.

Источник: воркер `temp_worker.py`, топик `sensors/temperature/{sensor_id}`.

**Валидация на сервере:**
- Ключ должен соответствовать regex `^[0-9a-f]{2}-[0-9a-f]{12}$`
- Значение должно соответствовать regex `^HDW:-?\d+(\.\d+)?, OUT:-?\d+(\.\d+)?$`
- Допустимый диапазон температур: от −55.0 до +125.0 °C (физический предел DS18B20)

#### `distance_mm` (int, опционально)

Расстояние от датчика до земли/препятствия в миллиметрах.

- Диапазон: 1 – 8190 мм (рабочий диапазон VL53L0X)
- Значение `8190` (0x1FFE) или отсутствие поля означает "цель вне диапазона"

Источник: воркер `distance_worker.py`, топик `sensors/distance`, датчик VL53L0X (лазерный дальномер, I²C).

#### `power_phases` (object, опционально — эмуляция, в перспективе реальные датчики)

Состояние трёх фаз электропитания на объекте.

| Ключ | Тип    | Значение                                   |
|------|--------|--------------------------------------------|
| `L1` | `bool` | `true` — напряжение присутствует на фазе L1 |
| `L2` | `bool` | `true` — напряжение присутствует на фазе L2 |
| `L3` | `bool` | `true` — напряжение присутствует на фазе L3 |

**Текущий статус:** значения эмулируются (см. раздел 7). При интеграции реальных датчиков
формат поля не изменится.

#### `battery` (object, опционально — эмуляция)

Состояние резервной аккумуляторной батареи (эмуляция высокого уровня).

| Ключ            | Тип     | Допустимые значения                                           |
|-----------------|---------|---------------------------------------------------------------|
| `battery_state` | `string`| `"charging"`, `"discharging"`, `"idle"`                       |

**Примечание:** это поле — эмуляция на основе состояния фаз. Реальные данные о DC-питании
(напряжение, ток, расчётный режим) передаются в поле `system_power` от INA219.

#### `wind` (object, опционально)

Скорость ветра.

| Ключ             | Тип    | Ед. изм. | Диапазон    |
|------------------|--------|----------|-------------|
| `wind_speed_mps` | `float`| м/с      | 0.0 – 30.0  |

Источник: воркер `wind_worker_ads1115.py`, топик `sensors/wind`.
Датчик: ADS1115 (АЦП) + аналоговый датчик ветра, I²C.

#### `tilt` (object, опционально)

Угол отклонения вышки от вертикали.

| Ключ           | Тип    | Ед. изм. | Описание                                      |
|----------------|--------|----------|-----------------------------------------------|
| `tilt_degrees` | `float`| градусы  | Абсолютное отклонение, >= 0. Критично при >5° |

Источник: воркер `mpu6050_direct.py`, топик `sensors/tilt`, датчик MPU6050 (акселерометр/гироскоп, I²C).

#### `system_power` (object, опционально, добавлено в v1.1.0)

Реальные показания DC-шины питания от INA219. Это поле позволяет серверу достоверно определить,
от чего питается устройство: от внешнего источника или от резервной АКБ.

| Ключ            | Тип     | Ед. изм. | Описание |
|-----------------|---------|----------|----------|
| `bus_voltage_v` | `float` | В        | Напряжение на шине (после шунта, т.е. напряжение нагрузки) |
| `current_ma`    | `float` | мА       | Ток через шунт. **Положительный** (+): потребление от шины / заряд АКБ. **Отрицательный** (−): разряд АКБ / отдача в шину |
| `power_mode`    | `string`| —        | Расчётный режим питания (см. таблицу ниже) |

**Возможные значения `power_mode`:**

| Режим          | Условие                                        | Физический смысл                                      |
|----------------|------------------------------------------------|-------------------------------------------------------|
| `"charging"`   | `current_ma` > +50 мА                          | Внешнее питание присутствует, идёт заряд резервной АКБ|
| `"discharging"`| `current_ma` < −50 мА                          | Внешнее питание отсутствует, система питается от АКБ  |
| `"external"`   | |current_ma| ≤ 50 мА и `bus_voltage_v` ≥ 4.5 В | Внешнее питание присутствует, АКБ не заряжается и не разряжается |
| `"battery"`    | `bus_voltage_v` < 4.5 В                        | Низкое напряжение — вероятно, только от АКБ           |

Источник: воркер `ina219_reader.py`, топик `sensors/system_power`, датчик INA219 (I²C).

## 5. Система алертов

### 5.1. Общие сведения

| Параметр      | Значение                          |
|---------------|-----------------------------------|
| Топик         | `ams/{device_id}/alert`           |
| QoS           | 1                                 |
| Отправка      | Немедленно при наступлении условия|
| Кулдаун       | 120 секунд на каждый тип алерта   |
| Формат        | JSON                              |

Алерты отправляются **независимо** от телеметрии и не ждут интервала `INTERVAL`.

### 5.2. Структура сообщения

```json
{
  "device_id": "AMS-000001",
  "alert_type": "overheat",
  "severity": "critical",
  "value": 87.3,
  "threshold": 85.0,
  "message": "Перегрев оборудования: 87.3°C",
  "timestamp": "2025-04-17T12:34:56Z"
}
```

### 5.3. Поля алерта

| Поле         | Тип     | Обязательное| Описание                                                                               |
|--------------|---------|:-----------:|----------------------------------------------------------------------------------------|
| `device_id`  | `string`| Да          | Идентификатор вышки                                                                    |
| `alert_type` | `string`| Да          | Тип алерта (допустимые значения — см. таблицу 5.4)                                     |
| `severity`   | `string`| Да          | `"critical"` — критично, требует реакции; `"warning"` — предупреждение                 |
| `value`      | `float` | Да          | Текущее значение параметра. Для `power_state_change` всегда `0`                        |
| `threshold`  | `float` | Да          | Пороговое значение. Для `power_state_change` всегда `0`                                |
| `message`    | `string`| Да          | Человекочитаемое описание события на русском языке                                     |
| `timestamp`  | `string`| Да          | Время события в ISO 8601, UTC, с точностью до секунд. Пример: `"2025-04-17T12:34:56Z"` |

### 5.4. Типы алертов

| `alert_type`           | `severity`  | Условие срабатывания                                           | Порог        |
|------------------------|-------------|----------------------------------------------------------------|--------------|
| `overheat`             | `critical`  | Любое значение HDW в `temperatures` превышает 85 °C            | 85.0 °C      |
| `high_wind`            | `warning`   | `wind_speed_mps` > 10 м/с                                      | 10.0 м/с     |
| `excessive_tilt`       | `critical`  | `tilt_degrees` > 5°                                            | 5.0°         |
| `power_state_change`   | `warning`   | Изменилось состояние любой фазы (L1/L2/L3) или `battery_state` | —            |
| `watchdog`             | `warning`   | Данные любого типа не обновлялись дольше таймаута              | см. табл. 5.5|

**Кулдаун:** 120 секунд. Алерт одного типа не отправляется повторно, если с момента
предыдущей отправки прошло менее 120 секунд.

### 5.5. Watchdog-таймауты

Агрегатор проверяет время последнего обновления каждого типа данных каждые 60 секунд.
Если данные не поступали дольше таймаута — генерируется алерт `watchdog` с `alert_type = "watchdog"`.

| Тип данных       | Таймаут | Нормальный интервал | Источник                    | Примечание                       |
|------------------|---------|---------------------|-----------------------------|----------------------------------|
| `temperature`    | 120 с   | ~3 с                | `temp_worker.py`            | Множественные датчики 1-Wire     |
| `distance`       | 30 с    | ~3 с                | `distance_worker.py`        | VL53L0X                          |
| `wind`           | 30 с    | ~3 с                | `wind_worker_ads1115.py`    | ADS1115 + аналоговый датчик      |
| `tilt`           | 30 с    | ~3 с                | `mpu6050_direct.py`         | MPU6050                          |
| `power`          | 120 с   | ~30 с               | эмуляция в агрегаторе       | Только при EMULATION_ENABLED     |
| `battery`        | 120 с   | ~30 с               | эмуляция в агрегаторе       | Только при EMULATION_ENABLED     |
| `system_power`   | 30 с    | ~3 с                | `ina219_reader.py`          | INA219 (v1.1.0)                  |

Если данные определённого типа ни разу не поступали с момента запуска агрегатора,
watchdog-алерт для этого типа не генерируется.

## 6. Входящие команды (сервер → устройство)

### 6.1. `set_uid` — назначение постоянного идентификатора

| Параметр       | Значение                                      |
|----------------|-----------------------------------------------|
| Контекст       | Только в режиме регистрации                   |
| Топик          | `ams-reg/{temp_uid}/command`                  |
| QoS            | 1                                             |

```json
{
  "command": "set_uid",
  "uid": "AMS-000001"
}
```

**Поля запроса:**

| Поле      | Тип     | Обязательное| Описание                                      |
|-----------|---------|:-----------:|-----------------------------------------------|
| `command` | `string`| Да          | Всегда `"set_uid"`                            |
| `uid`     | `string`| Да          | Постоянный идентификатор, формат `AMS-XXXXXX` |

**Ответ:** устройство не отправляет подтверждения — после сохранения UID оно выполняет
`sudo reboot`. Сервер может считать операцию успешной, если через ~30–60 секунд устройство
начинает публиковать телеметрию в `ams/{uid}/telemetry`.

### 6.2. `calibrate_tilt` — калибровка наклона

| Параметр       | Значение                               |
|----------------|----------------------------------------|
| Контекст       | Основной режим                         |
| Топик          | `ams/{device_id}/command`              |
| QoS            | 1                                      |

```json
{
  "command": "calibrate_tilt"
}
```

**Поля запроса:**

| Поле      | Тип     | Обязательное| Описание                  |
|-----------|---------|:-----------:|---------------------------|
| `command` | `string`| Да          | Всегда `"calibrate_tilt"` |

**Действие:** устройство сохраняет текущее значение `tilt_degrees` как смещение в файл
`~/fw_settings/tilt_calib.json`. При последующих измерениях наклона это смещение вычитается,
что позволяет обнулить наклон после физической установки вышки.

## 7. Эмуляция

Эмуляция управляется флагом `EMULATION_ENABLED` в коде агрегатора. Когда флаг `true`,
агрегатор публикует в локальный MQTT синтетические данные *в дополнение* к реальным.

### 7.1. Эмулируемые топики

| Локальный топик    | Данные                                            | Период |
|--------------------|---------------------------------------------------|--------|
| `sensors/power`    | `{"phases": {"L1": bool, "L2": bool, "L3": bool}}`| 30 с   |
| `sensors/battery`  | `{"battery_state": "charging"|"discharging"|"idle"}`| 30 с |

**Логика эмуляции `sensors/power`:**
Каждая фаза независимо: 75% — `true`, 25% — `false`.

**Логика эмуляции `sensors/battery`:**
- Если все три фазы `false` → `"discharging"`
- Иначе → случайно `"charging"` или `"idle"` (50/50)

### 7.2. Реальные топики (публикуются воркерами, не эмуляцией)

| Локальный топик              | Воркер                    | Датчик                 | Шина    |
|------------------------------|---------------------------|------------------------|---------|
| `sensors/temperature/{id}`   | `temp_worker.py`          | DS18B20                | 1-Wire  |
| `sensors/distance`           | `distance_worker.py`      | VL53L0X                | I²C     |
| `sensors/wind`               | `wind_worker_ads1115.py`  | ADS1115 + аналоговый   | I²C     |
| `sensors/tilt`               | `mpu6050_direct.py`       | MPU6050                | I²C     |
| `sensors/system_power`       | `ina219_reader.py`        | INA219                 | I²C     |

## 8. Сводная таблица датчиков

| # | Воркер                     | Датчик            | Измеряемый параметр              | Ед. изм. | Точность    | Период |
|---|----------------------------|-------------------|----------------------------------|----------|-------------|--------|
| 1 | `temp_worker.py`           | DS18B20           | Температура (HDW / OUT)          | °C       | ±0.5 °C     | ~3 с   |
| 2 | `distance_worker.py`       | VL53L0X           | Расстояние до препятствия        | мм       | ±3% (до 2 м)| ~3 с   |
| 3 | `wind_worker_ads1115.py`   | ADS1115 + аналог. | Скорость ветра                   | м/с      | ±0.5 м/с    | ~3 с   |
| 4 | `mpu6050_direct.py`        | MPU6050           | Угол отклонения от вертикали     | °        | ±0.5°       | ~3 с   |
| 5 | `ina219_reader.py`         | INA219            | Напряжение / ток DC-шины         | В / мА   | ±1%         | ~3 с   |

Все I²C-воркеры используют общую шину через модуль `i2c_helpers.py`
(функции `get_shared_i2c_bus()` / `release_shared_i2c_bus()`) для предотвращения конфликтов.

## 9. Рекомендации backend-разработчику

### 9.1. Валидация входящих сообщений

- **`device_id`**: проверять, что устройство зарегистрировано в системе.
- **`timestamp`** в алертах: парсить как ISO 8601, приводить к UTC.
- **`temperatures`**: валидировать ключи и значения по regex (см. п. 4.4).
- **Неизвестные поля**: игнорировать (прямая совместимость при добавлении новых полей).
- **Отсутствующие поля**: считать `null` / отсутствующими, не падать с ошибкой.

### 9.2. Обработка дубликатов

QoS 1 гарантирует доставку, но допускает дубликаты. Сервер должен быть идемпотентным:
дедупликация по `(device_id, timestamp)` или хранение последнего значения на запись.

### 9.3. Мониторинг состояния устройства

Сервер должен отслеживать:

1. **Регулярность телеметрии:** если сообщений нет > 120 секунд — устройство офлайн.
2. **Watchdog-алерты:** при получении `watchdog` алерта — конкретный воркер на устройстве не отвечает.
3. **`power_mode`:** при `"discharging"` или `"battery"` — устройство на резервном питании, может скоро отключиться.
